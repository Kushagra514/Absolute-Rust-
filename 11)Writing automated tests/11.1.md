# 🧪 1. TEST KYA HOTA HAI?

Test ek Rust function hota hai jo check karta hai ki
hamara normal/non-test code expected tarike se kaam kar raha hai ya nahi.

Ek typical test ke 3 steps:

    1. Setup
       ↓
    required data/state prepare karo

    2. Run
       ↓
    jis code ko test karna hai use chalao

    3. Assert
       ↓
    check karo result expected hai ya nahi


Simple flow:

    Setup
      ↓
    Run code
      ↓
    Check result
      ↓
    PASS / FAIL


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 🧩 2. `#[test]` ATTRIBUTE

Normal function ko test function banane ke liye:

    #[test]
    fn it_works() {
        ...
    }

`#[test]` ek attribute hai.

Meaning:

> "Rust test runner, is function ko test ki tarah run karna."

Important:

    #[test]
    ↓
    function test hai

Without:

    #[test]

function sirf normal helper function ho sakta hai;
test runner usse test ke roop mein run nahi karega.

Ek `tests` module mein multiple test functions ho sakte hain.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 🏗️ 3. `cargo new --lib` TEST TEMPLATE

Jab library project create karte ho:

    cargo new adder --lib

Cargo automatically `src/lib.rs` mein example test
generate karta hai.

Typical structure:

    pub fn add(left: u64, right: u64) -> u64 {
        left + right
    }

    #[cfg(test)]
    mod tests {
        use super::*;

        #[test]
        fn it_works() {
            let result = add(2, 2);
            assert_eq!(result, 4);
        }
    }

# ⚙️ 4. `#[cfg(test)]` KYA KARTA HAI?

Important:

    #[cfg(test)]

**tests module create nahi karta.**

`mod tests` already module hai:

    mod tests {
        ...
    }

`#[cfg(test)]` ka meaning:

> **Is module ko testing configuration mein compile karo.**

So:

    #[cfg(test)]
    mod tests {
        ...
    }

Normal build:

    cargo build
         ↓
    tests module compile nahi

Testing:

    cargo test
         ↓
    tests module compile


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 📦 5. `use super::*;` KYUN?

Example:

    #[cfg(test)]
    mod tests {
        use super::*;

        #[test]
        fn it_works() {
            let result = add(2, 2);
            assert_eq!(result, 4);
        }
    }

`tests` ek inner module hai.

Outer module mein:

    add()

defined hai.

Inner `tests` module ko outer module ke items scope mein
laane ke liye:

    use super::*;

likhte hain.

Meaning:

    super
      ↓
    parent/outer module

    *
      ↓
    us module ke items

So:

    use super::*;

means roughly:

> **Parent module ke available items ko tests module ke
> scope mein lao.**

# 📚 9. `Doc-tests`

`cargo test` output mein kabhi:

    Doc-tests adder

dikhega.

Rust documentation mein code examples likhe ja sakte hain.

Rust un examples ko bhi compile/test kar sakta hai.

Purpose:

    Documentation
          +
    Actual code
          ↓
       sync mein rakho

Agar documentation mein example code future mein
invalid ho jaye, documentation test us problem ko
catch kar sakta hai.

Example:

    Doc-tests adder

    running 0 tests

Agar koi documentation test nahi hai,
toh 0 tests dikh sakte hain.

# ❌ 10. TEST KAB FAIL HOTA HAI?

Rust test fail hota hai jab test function panic karta hai.

Example:

    #[test]
    fn another() {
        panic!("Make this test fail");
    }

Flow:

    test run
       ↓
    panic!
       ↓
    test thread dies
       ↓
    test FAILED


Each test ek separate thread mein run hota hai.

Main test thread dekhta hai ki test thread fail hua ya nahi.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 🔥 11. `panic!` TEST FAILURE

Agar:

    #[test]
    fn another() {
        panic!("Make this test fail");
    }

toh output roughly:

    test tests::another ... FAILED

Aur failure details mein:

    thread 'tests::another' panicked
    ...
    Make this test fail

End mein:

    test result: FAILED.
    1 passed; 1 failed;

Example:

Phir:

    failures:
        tests::another

Ye useful hai jab bahut saare tests hon.

# ✅ 13. `assert!` MACRO

`assert!` check karta hai ki given expression:

    true

hai ya nahi.

Example:

    assert!(larger.can_hold(&smaller));


Agar:

    expression == true
        ↓
    test continues
        ↓
    PASS


Agar:

    expression == false
        ↓
    assert! calls panic!
        ↓
    test FAIL


So:

    assert!(condition)

means:

> **Condition true honi chahiye.**


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 📐 14. `assert!` EXAMPLE

    #[test]
    fn larger_can_hold_smaller() {

        let larger = Rectangle {
            width: 8,
            height: 7,
        };

        let smaller = Rectangle {
            width: 5,
            height: 1,
        };

        assert!(larger.can_hold(&smaller));
    }


Expected:

    larger.can_hold(&smaller)
              ↓
             true

Therefore:

    assert!(true)
         ↓
       PASS


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 🔄 15. `assert!` WITH EXPECTED FALSE

Suppose:

    smaller.can_hold(&larger)

ka expected result:

    false

To test this:

    assert!(!smaller.can_hold(&larger));

Because:

    smaller.can_hold(&larger)
              ↓
            false

    !false
      ↓
    true

    assert!(true)
        ↓
       PASS


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 🐛 16. TESTS BUG CATCH KARTE HAIN

Suppose correct code:

    self.width > other.width
    &&
    self.height > other.height


Galti se:

    self.width < other.width
    &&
    self.height > other.height

kar diya.

Tests:

    larger_can_hold_smaller
          ↓
        FAILED

    smaller_cannot_hold_larger
          ↓
          ok

Meaning:

> **Tests ne implementation mein bug detect kar liya.**

This is one of the main purposes of testing.

# ⚖️ 17. `assert_eq!`

Jab expected value aur actual value ko compare karna ho:

    assert_eq!(actual, expected);

Example:

    let result = add_two(2);

    assert_eq!(result, 4);


Meaning:

    result == 4 ?
        ↓
      YES → PASS
      NO  → FAIL


`assert_eq!` internally equality comparison use karta hai.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# ❗ 18. `assert_eq!` FAILURE PAR EXTRA INFORMATION

Suppose:

    result = 5

but:

    expected = 4

Then:

    assert_eq!(result, 4);

failure output mein:

    assertion `left == right` failed
      left: 5
     right: 4

Ye bahut useful hai because immediately pata chalta hai:

    actual value = 5
    expected value = 4


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 🧠 19. `left` AUR `right`

Rust equality assertion mein:

    left
      ↓
    first argument

    right
      ↓
    second argument

Example:

    assert_eq!(result, 4);

    left  = result
    right = 4

Lekin:

    assert_eq!(4, result);

bhi same logical equality check karta hai.

Rust mein expected value ko first rakhna compulsory nahi hai.

Unlike some testing frameworks, Rust yahan arguments ko
simply `left` aur `right` ke naam se report karta hai.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 🔀 20. `assert_ne!`

`assert_ne!` check karta hai ki two values:

    NOT equal

hon.

Example:

    assert_ne!(result, original);

Pass:

    result != original

Fail:

    result == original


Useful jab:

> Exact value pata nahi hai,
> lekin pata hai ki result kisi particular value ke
> equal nahi hona chahiye.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 🔍 21. `assert!` VS `assert_eq!` VS `assert_ne!`

    assert!(condition)
        ↓
    condition true honi chahiye


    assert_eq!(a, b)
        ↓
    a == b hona chahiye


    assert_ne!(a, b)
        ↓
    a != b hona chahiye


Failure information:

    assert!
        ↓
    mainly condition false batata hai

    assert_eq!
        ↓
    compared values bhi print karta hai

    assert_ne!
        ↓
    compared values bhi print kar sakta hai


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 🧩 22. `PartialEq` AUR `Debug` KYUN CHAHIYE?

`assert_eq!` aur `assert_ne!` internally:

    ==
    !=

operators use karte hain.

Isliye compared type ko:

    PartialEq

implement karna chahiye.

Failure par values ko debug format mein print karne ke liye:

    Debug

bhi required hai.


So:

    assert_eq!
        ↓
    PartialEq
        +
    Debug

# 🏗️ 23. STRUCT KE SAATH YE KYUN DIKHAYA?

Suppose apna custom type:

    struct Rectangle {
        width: u32,
        height: u32,
    }

Rust ko automatically nahi pata ki:

    Rectangle == Rectangle

kaise compare karna hai.

Isliye:

    #[derive(PartialEq, Debug)]
    struct Rectangle {
        width: u32,
        height: u32,
    }

Now:

    PartialEq
       ↓
    equality comparison

    Debug
       ↓
    failure par value print karna


Important:

Ye sirf `struct` ke liye nahi hai.

**Structs aur enums jo tum khud define karte ho, unke liye
required traits manually implement ya derive karne pad sakte hain.**

# 📝 24. CUSTOM FAILURE MESSAGE

Assertions mein custom message bhi de sakte ho.

Example:

    assert!(
        result.contains("Carol"),
        "Greeting did not contain name, value was `{result}`"
    );


Agar assertion fail:

    default failure
          +
    custom message

show hoga.

Custom message useful hai because:

> Failure ka context immediately samajh aata hai.

# 🧠 25. CUSTOM MESSAGE KA SYNTAX

Ye arguments:

    assert!(
        condition,
        "message {}",
        value
    );

`format!` jaise formatting rules follow karte hain.

So `{}` placeholders use kar sakte ho.

Example:

    assert!(
        result.contains("Carol"),
        "Got `{result}` instead"
    );

# 🎯 26. EXACT EQUALITY VS PROPERTY TESTING

Suppose:

    fn greeting(name: &str) -> String {
        format!("Hello {name}!")
    }

Requirement sirf:

> Output mein user ka naam hona chahiye.

Toh:

    assert_eq!(
        result,
        "Hello Carol!"
    );

too strict ho sakta hai.

Agar future mein greeting:

    "Hi Carol!"

ban jaye aur requirement still valid ho,
test unnecessarily fail ho jayega.

Better:

    assert!(result.contains("Carol"));

Meaning:

> **Hum exact output nahi,
> required property test kar rahe hain.**

Test ko actual requirement ke according design karna chahiye.

# 💥 27. `#[should_panic]`

Kabhi expected behavior hi panic karna hota hai.

Example:

    Guess::new(200)

Agar rule hai:

    Guess value must be 1..=100

toh invalid value par:

    panic!

expected hai.

Test:

    #[test]
    #[should_panic]
    fn greater_than_100() {
        Guess::new(200);
    }


Meaning:

> **Ye test tab PASS hoga jab function panic karega.**

Flow:

    test
      ↓
    Guess::new(200)
      ↓
    panic!
      ↓
    expected panic
      ↓
    PASS


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# ⚠️ 28. `#[should_panic]` ULTA LOGIC

Normal test:

    no panic
       ↓
    PASS

`#[should_panic]` test:

    panic
       ↓
    PASS

And:

    no panic
       ↓
    FAIL


So:

    #[should_panic]

means:

> **"Is test ke andar panic expected hai."**

# 🧪 29. `#[should_panic]` TEST FAIL KAB HOGA?

Suppose:

    #[should_panic]
    fn greater_than_100() {
        Guess::new(200);
    }

Lekin implementation mein bug aa gaya aur:

    Guess::new(200)

panic nahi karta.

Then:

    test did not panic as expected
          ↓
        FAILED


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# ⚠️ 30. `#[should_panic]` KI LIMITATION

Simple:

    #[should_panic]

sirf ye check karta hai:

    panic hua?
       ↓
      YES

But ye necessarily check nahi karta ki:

> **Correct reason se panic hua?**

Example:

Expected:

    Guess::new(200)
       ↓
    panic:
    "must be less than or equal to 100"

But code mein kisi completely different bug ki wajah se:

    panic!("some unrelated error")

ho gaya.

Simple `#[should_panic]` test phir bhi pass ho sakta hai.

Therefore more precise testing ke liye:

    expected


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 🎯 31. `#[should_panic(expected = "...")]`

Example:

    #[test]
    #[should_panic(
        expected = "less than or equal to 100"
    )]
    fn greater_than_100() {
        Guess::new(200);
    }

Now test require karta hai:

    panic hona chahiye
          AND
    panic message mein
    specified text hona chahiye


Flow:

    panic?
      ↓
    YES
      ↓
    message contains expected text?
      ↓
    YES → PASS
    NO  → FAIL

# 🔍 32. `expected` FULL MESSAGE HONA ZAROORI NAHI

Example:

    #[should_panic(
        expected = "less than or equal to 100"
    )]

Actual panic:

    "Guess value must be less than or equal to 100, got 200."

Test pass karega because expected text actual message
ka substring hai.

So:

    expected = "less than or equal to 100"

actual:

    "Guess value must be less than or equal to 100, got 200."

    ↓

    substring present
        ↓
      PASS


Tum full message bhi specify kar sakte ho agar exactness chahiye.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 🐛 33. `#[should_panic(expected = ...)]` BUG CATCH KAR SAKTA HAI

Suppose:

    Guess::new(200)

galti se wrong panic message deta hai:

    "must be greater than or equal to 1"

But test expects:

    "less than or equal to 100"

Then:

    panic hua
       ↓
    YES

but:

    expected substring nahi mila
       ↓
    FAIL


Isse pata chalta hai:

> Panic hua tha, lekin expected reason/message wala panic nahi tha.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 📦 34. TESTS MEIN `Result<T, E>` USE KARNA

Tests sirf panic/assertions se hi fail nahi hone chahiye.

Test function `Result<T, E>` bhi return kar sakta hai.

Example:

    #[test]
    fn it_works() -> Result<(), String> {

        let result = add(2, 2);

        if result == 4 {
            Ok(())
        } else {
            Err(String::from(
                "two plus two does not equal four"
            ))
        }
    }


Meaning:

    correct
      ↓
    Ok(())

    incorrect
      ↓
    Err(message)


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 🔄 35. `Result<(), String>` KA MATLAB

Return type:

    Result<(), String>

means:

    Success → ()
    Failure → String


Test successful:

    Ok(())

Test failed:

    Err(String::from("..."))


Yahan test failure ke liye:

    panic!

directly call karne ki zaroorat nahi.

Test framework `Err` ko failure ke roop mein treat karega.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# ❓ 36. TESTS MEIN `Result` KA BENEFIT

`Result<T, E>` returning tests ka important benefit:

    ?

operator use kar sakte ho.

Example conceptually:

    let value = some_operation()?;

Agar operation:

    Ok(value)
       ↓
    continue

Agar:

    Err(error)
       ↓
    test returns Err
       ↓
    test FAIL


So `Result` tests convenient hain jab test ke andar
multiple operations `Result` return karte hain.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# ⚠️ 37. `#[should_panic]` + `Result` SAATH NAHI

Agar test:

    Result<T, E>

return karta hai,

toh us par:

    #[should_panic]

use nahi kar sakte.

Why?

Because:

    #[should_panic]
        ↓
    panic expected

while:

    Result test
        ↓
    Err represents failure


Dono mechanisms different hain.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 🚨 38. `Result` MEIN EXPECTED `Err` TEST KARNA

Agar specifically check karna hai ki operation:

    Err

return karega,

toh `?` use mat karo.

Instead:

    assert!(value.is_err());

Example concept:

    let result = some_operation();

    assert!(result.is_err());


Because:

    result.is_err()
        ↓
    true if Err
        ↓
    assert! passes


Agar:

    result.is_ok()

hua:

    assert!(false)
        ↓
    FAIL


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 🧠 39. COMPLETE TESTING MENTAL MODEL

                    cargo test
                        ↓
                test runner binary
                        ↓
                #[test] functions
                        ↓
              ┌─────────┴─────────┐
              ↓                   ↓
            PASS                FAIL
              ↓                   ↓
          assertion              panic
          successful          assertion failed
              │                   │
              │                   │
              └─────────┬─────────┘
                        ↓
                  test report


Different ways to check:

    assert!(condition)
          ↓
    condition true


    assert_eq!(a, b)
          ↓
    a == b


    assert_ne!(a, b)
          ↓
    a != b


    #[should_panic]
          ↓
    panic expected


    #[should_panic(expected = "...")]
          ↓
    panic + expected message


    Result<(), E>
          ↓
    Ok = pass
    Err = fail

# 🔑 40. MOST IMPORTANT DIFFERENCES

### `#[test]`

    Function ko test banata hai.


### `#[cfg(test)]`

    Tests module ko testing configuration mein compile karta hai.

    IMPORTANT:
    Ye tests module create nahi karta.


### `cargo test`

    Tests compile + run karta hai.


### `assert!`

    Boolean condition true honi chahiye.


### `assert_eq!`

    Two values equal honi chahiye.


### `assert_ne!`

    Two values unequal honi chahiye.


### `#[should_panic]`

    Panic expected hai.


### `#[should_panic(expected = "...")]`

    Panic + specific message substring expected hai.


### `Result<T, E>` test

    Ok → pass
    Err → fail

# ⭐ 41. KEY TAKEAWAYS

🔹 Test = code ke expected behavior ko verify karne wala function.

🔹 Typical test flow:

       Setup → Run → Assert

🔹 `#[test]` test runner ko batata hai ki function test hai.

🔹 `#[cfg(test)]` tests module ko testing time par compile
   karne ke liye use hota hai.

🔹 `cargo test` test runner binary build karke tests run karta hai.

🔹 Tests alag threads mein run hote hain.

🔹 Test panic kare → test FAIL.

🔹 `assert!(condition)` condition false hone par panic karta hai.

🔹 `assert_eq!(a, b)` equality check karta hai aur failure par
   compared values print karta hai.

🔹 `assert_ne!(a, b)` inequality check karta hai.

🔹 `assert_eq!` / `assert_ne!` ke liye compared values ko
   `PartialEq` aur failure printing ke liye `Debug` chahiye.

🔹 Custom structs/enums ke liye commonly:

       #[derive(PartialEq, Debug)]

🔹 Custom assertion message debugging ko easier banata hai.

🔹 Exact output test karne ki jagah required property test karna
   kabhi better hota hai.

🔹 `#[should_panic]` ka matlab:
   panic hona expected hai.

🔹 `#[should_panic]` alone wrong reason ke panic ko bhi accept
   kar sakta hai.

🔹 `expected = "..."` panic message mein expected substring
   check karta hai.

🔹 Tests `Result<T, E>` return kar sakte hain.

🔹 `Result` test mein:

       Ok(()) → success
       Err(...) → failure

🔹 `Result` returning tests `?` operator use kar sakte hain.

🔹 `#[should_panic]` ko `Result<T, E>` returning test ke saath
   use nahi kar sakte.

🔹 Expected `Err` ko test karna ho toh `?` ke bajay:

       assert!(value.is_err());

   use karo.

🔹 `Doc-tests` documentation ke code examples ko compile/test
   karke docs ko actual code ke saath sync rakhne mein help karte hain.
