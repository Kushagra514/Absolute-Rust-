# 🧪 1. RUST MEIN TESTS KE 2 MAIN TYPES

Rust testing mein mainly 2 categories hain:

    1. Unit Tests
    2. Integration Tests


### Unit Tests

    small
    focused
    ek module/code unit ko isolation mein test karte hain

    ↓

    private functions bhi test kar sakte hain


### Integration Tests

    library ke bahar se test karte hain

    ↓

    sirf public API use kar sakte hain

    ↓

    multiple modules/parts ko saath test kar sakte hain


Simple difference:

    Unit Test
        ↓
    "Ye particular piece of code sahi hai?"


    Integration Test
        ↓
    "Library ke different parts
     saath mein sahi kaam kar rahe hain?"


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 🎯 2. DONO TYPES KE TESTS KYUN IMPORTANT HAIN?

Suppose library mein:

    Module A
       ↓
      works

    Module B
       ↓
      works

Lekin:

    A + B
       ↓
    integration problem

Isliye:

    Unit Tests
        ↓
    individual pieces check


    Integration Tests
        ↓
    pieces together check


Dono milkar ensure karte hain ki:

    separately bhi correct
    +
    together bhi correct

# 🔬 3. UNIT TESTS KAHAN LIKHTE HAIN?

Unit tests generally:

    src/

directory mein
usi file ke andar likhe jaate hain
jisme test kiya ja raha code hai.

Example:

    src/lib.rs

    ↓

    actual code
    +
    tests module


Convention:

    #[cfg(test)]
    mod tests {
        ...
    }


Typical structure:

    src/
    └── lib.rs

        actual code

        #[cfg(test)]
        mod tests {
            test functions
        }

# ⚙️ 4. `#[cfg(test)]` KA ACTUAL PURPOSE

Example:

    #[cfg(test)]
    mod tests {
        ...
    }

`cfg` ka meaning:

    configuration

Rust ko batata hai:

> "Is code ko particular configuration mein hi include karo."

Yahan configuration hai:

    test


So:

    #[cfg(test)]

means:

> **Testing configuration mein hi is module ko compile karo.**


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 🏗️ 5. `#[cfg(test)]` KAB ACTIVE HOTA HAI?

### `cargo build`

    cargo build
        ↓
    normal build
        ↓
    #[cfg(test)] code
        ↓
    NOT included


### `cargo test`

    cargo test
        ↓
    test configuration
        ↓
    #[cfg(test)] code
        ↓
    included


So:

    #[cfg(test)]
          ↓
    test code only when testing


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 💾 6. `#[cfg(test)]` USE KARNE KA FAYDA

Unit tests same source files mein hote hain.

Agar test code normal compiled library mein bhi include ho,
toh:

    compile time ↑
    compiled artifact ka size ↑


`#[cfg(test)]` ki wajah se:

    normal build
        ↓
    test code excluded

Therefore:

    less compile work
    +
    smaller compiled artifact


Important:

`#[cfg(test)]` sirf `#[test]` functions par apply nahi hota.

Module ke andar ke:

    test functions
    +
    helper functions

sab test configuration ke andar compile hote hain.

# 🧩 7. STANDARD UNIT TEST STRUCTURE

Example:

    pub fn add(left: u64, right: u64) -> u64 {
        left + right
    }

    #[cfg(test)]
    mod tests {

        use super::*;

        #[test]
        fn it_works() {
            let result = add(2, 2);
            assert_eq!(result, 4);
        }
    }


Structure:

    actual code
        ↓
    #[cfg(test)]
    mod tests
        ↓
    #[test]
    function

# 🔑 8. `use super::*` UNIT TESTS MEIN

Tests module:

    mod tests

parent module ke andar hota hai.

Example:

    lib.rs
      │
      ├── add()
      │
      └── mod tests
              │
              └── test


`tests` module ke andar:

    use super::*;

likhne se parent module ke items scope mein aa jaate hain.

So test directly:

    add(2, 2)

call kar sakta hai.


`super`

    ↓

parent module


`*`

    ↓

parent module ke items

# 🔒 9. UNIT TESTS PRIVATE FUNCTIONS KO TEST KAR SAKTE HAIN

Rust mein unit tests:

    private functions

ko bhi test kar sakte hain.

Example:

    pub fn add_two(a: u64) -> u64 {
        internal_adder(a, 2)
    }

    fn internal_adder(left: u64, right: u64) -> u64 {
        left + right
    }


`internal_adder`:

    ❌ pub nahi hai
    ↓
    private function


Lekin test:

    #[cfg(test)]
    mod tests {

        use super::*;

        #[test]
        fn internal() {
            let result = internal_adder(2, 2);
            assert_eq!(result, 4);
        }
    }


work karega.

# 🧠 10. PRIVATE FUNCTION ACCESS KYUN POSSIBLE HAI?

Important concept:

> **Tests bhi normal Rust code hi hain.**

Aur:

    tests

ek child module hai.

Rust mein child module apne ancestor/parent modules
ke items access kar sakta hai.

`use super::*` parent ke items ko scope mein laata hai.

Therefore:

    private function
          ↓
    parent module
          ↓
    child `tests` module
          ↓
    accessible


Important:

Rust tumhe private functions test karne se force nahi karta.

Whether private implementation details ko directly test karna
chahiye ya nahi, ye testing design decision hai.

# 🌐 11. INTEGRATION TESTS KYA HOTE HAIN?

Integration tests:

    library ke bahar

hote hain.

Ye library ko exactly us tarah use karte hain
jaise koi external user/another crate use karega.

Therefore:

    Integration Test
          ↓
    external perspective
          ↓
    public API only


Private functions directly access nahi kar sakte.

# 🔬 12. INTEGRATION TEST KA PURPOSE

Unit tests:

    individual units
        ↓
    separately correct?


Integration tests:

    multiple parts
        ↓
    together correctly working?


Possible situation:

    Module A → correct
    Module B → correct

but:

    A + B
      ↓
    incorrect interaction


Integration test isi type ke problems catch karne mein
important hai.

# 🚨 14. `tests/` DIRECTORY SPECIAL HAI

Cargo automatically:

    tests/

directory ko integration-test directory ke roop mein
recognize karta hai.

Isliye manually:

    #[cfg(test)]

lagane ki zaroorat nahi.


Example:

    tests/integration_test.rs

    #[test]
    fn it_adds_two() {
        ...
    }


No:

    #[cfg(test)]

needed.


Why?

Because Cargo already knows:

    tests/
       ↓
    integration tests

# 📦 15. EACH INTEGRATION TEST FILE = SEPARATE CRATE

Important concept:

    tests/integration_test.rs

ek separate crate ki tarah compile hoti hai.

Agar:

    tests/api_test.rs
    tests/database_test.rs

hain,

toh ye alag-alag test crates ki tarah compile hote hain.


Therefore integration test ko library ko explicitly
scope mein laana padta hai.

# 🔗 16. INTEGRATION TEST MEIN LIBRARY KO IMPORT KYUN KARTE HAIN?

Example:

    use adder::add_two;

Unit test mein:

    use super::*;

use kar sakte the.

But integration test external crate ki tarah behave karta hai.

Therefore:

    use adder::add_two;

Meaning:

> **`adder` library ke public API se `add_two` lao.**


Important:

Integration test ko library ka:

    public API

hi available hota hai.

Suppose:

    fn internal_adder() {
        ...
    }

private hai.

Integration test:

    use adder::internal_adder;

nahi kar sakta.

Because integration test:

    external code

ki tarah behave karta hai.

External code ko:

    pub

items hi available hote hain.


Difference:

    Unit Test
        ↓
    private + public


    Integration Test
        ↓
    public only

      FAIL

     ↓      ↓
 Integration STOP

 Doc-tests

Even though:

    integration tests ke liye available

    ❌ test output mein separate section nahi

# 🔗 29. `common` MODULE KO USE KAISE KARE?

`tests/common/mod.rs`:

    pub fn setup() {
        // setup code
    }


`tests/integration_test.rs`:

    mod common;
         ↓
    common module available
         ↓
    common::setup()
         ↓
    shared setup code run

Suppose project mein sirf:

    src/main.rs

hai.

No:

    src/lib.rs

    binary crate

hai.

> Integration tests external crate ki tarah library ko

    src/main.rs

Therefore:

    binary-only crate
        +
    no lib.rs
        ↓
    integration tests mein
    main.rs functions ko

# 🏗️ 32. BINARY + LIBRARY STRUCTURE KYUN USEFUL HAI?

Rust project mein common structure:

    src/
    ├── main.rs
    └── lib.rs


`lib.rs`:

    actual application logic
        ↓
    library functions


`main.rs`:

    small amount of code
        ↓
    library logic ko call karo


Architecture:

    src/main.rs
         ↓
    calls
         ↓
    src/lib.rs
         ↓
    application logic


Now integration tests:

    tests/
        ↓
    use library crate
        ↓
    test important logic


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 🎯 33. `main.rs` KO MINIMAL RAKHNE KA BENEFIT

Suppose:

    lib.rs
        ↓
    important business logic


    main.rs
        ↓
    simply calls library logic


Integration tests:

    lib.rs
        ↓
    important functionality test


Agar:

    lib.rs

correctly tested hai,

toh `main.rs` ka small amount of glue code
separately test karna generally unnecessary ho sakta hai.


Book ka recommended structure:

    main.rs
        ↓
    thin entry point

    lib.rs
        ↓
    important logic

    tests/
        ↓
    integration tests


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# ⚖️ 34. UNIT VS INTEGRATION — FINAL COMPARISON

    ┌─────────────────────────────────────────────┐
    │                 UNIT TEST                   │
    ├─────────────────────────────────────────────┤
    │ Location: src/                              │
    │ Same file as code                           │
    │ Focus: individual unit                      │
    │ Can test private functions                  │
    │ Usually #[cfg(test)]                        │
    │ Internal perspective                        │
    └─────────────────────────────────────────────┘


    ┌─────────────────────────────────────────────┐
    │             INTEGRATION TEST                │
    ├─────────────────────────────────────────────┤
    │ Location: tests/                            │
    │ External to library                         │
    │ Focus: multiple parts working together      │
    │ Public API only                             │
    │ No #[cfg(test)] needed                      │
    │ External-user perspective                   │
    └─────────────────────────────────────────────┘

# 🔑 36. KEY TAKEAWAYS

🔹 Rust testing ki 2 main categories hain:

       Unit Tests
       Integration Tests


🔹 Unit tests individual code units ko isolation mein test
   karte hain.

🔹 Unit tests `src/` directory mein, generally usi file mein
   likhe jaate hain jisme tested code hai.

🔹 Unit tests private functions ko bhi test kar sakte hain.

🔹 `#[cfg(test)]` ka meaning hai:
   test configuration mein hi code compile/include karo.

🔹 `#[cfg(test)]` unit-test module ko normal `cargo build`
   se exclude karta hai.

🔹 Isse normal build ka compile time aur compiled artifact
   size reduce hota hai.

🔹 `use super::*` tests module ke parent module ke items
   scope mein laata hai.

🔹 Integration tests library ke completely external hote hain.

🔹 Integration tests external user ki tarah library ko use karte hain.

🔹 Integration tests sirf public API access kar sakte hain.

🔹 Integration tests multiple modules/parts ke interaction ko
   test karte hain.

🔹 Integration tests top-level `tests/` directory mein hote hain.

🔹 Cargo `tests/` directory ko automatically integration-test
   directory samajhta hai.

🔹 Isliye integration test files mein `#[cfg(test)]` ki zaroorat nahi.

🔹 `tests/` ki har test file ek separate crate ke roop mein
   compile hoti hai.

🔹 Isliye integration test mein library ko explicitly import karte hain:

       use adder::add_two;


🔹 `cargo test` unit tests, integration tests aur doc tests
   ko run karta hai.

🔹 Agar kisi test section mein failure hota hai, following
   sections run nahi hote.

🔹 Specific integration test file run karne ke liye:

       cargo test --test integration_test


🔹 `tests/common.rs` ko Cargo integration test file samajh sakta hai,
   even if usmein koi test nahi ho.

🔹 Shared integration-test helper code ke liye:

       tests/common/mod.rs

   use karna better hai.

🔹 `tests/common/mod.rs` separate integration-test crate nahi banta.

🔹 Integration test file mein:

       mod common;

   karke helper module use kar sakte ho.

🔹 Binary-only crate jisme sirf `src/main.rs` hai, usmein
   integration tests `main.rs` ke functions ko library API ki
   tarah import nahi kar sakte.

🔹 Isliye important application logic ko `src/lib.rs` mein rakhna
   aur `src/main.rs` ko thin entry point rakhna useful hai.

# ⭐ ONE-LINE SUMMARY

> **Unit tests andar se individual pieces ko test karte hain
> (private code bhi), jabki integration tests bahar se public API
> ke through multiple pieces ko saath test karte hain.**
