## 🧠 FIRST MENTAL MODEL — RUST MEIN "STRING" EK HI CHEEZ NAHI HAI

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Rust ke core language mein string-related type:

```
str
```

Lekin practically ise mostly borrowed form mein dekha jaata hai:

```
&str
```

Isko:

```
string slice
```

kehte hain.

Standard library mein ek aur important type hai:

```
String
```

So basic distinction:

```
String
├── owns the data
├── growable
├── mutable
└── UTF-8 encoded

&str
├── borrows data
├── does not own the data
└── UTF-8 encoded
```

⚠️ IMPORTANT

Jab Rust Book ya Rust programmer casually "string" bolta hai, woh
context ke according `String` ya `&str` dono ko refer kar sakta hai.

Is section ka focus mainly `String` par hai, lekin `String` aur `&str`
dono Rust programming mein heavily used hote hain.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 1. DEFINING STRINGS

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

## 🔹 `str`

Rust ke core language mein ek string type hai:

```
str
```

Lekin normally hum ise directly use nahi karte.

Usually:

```
&str
```

ke form mein use karte hain.

### `&str` kya hai?

`&str` ek reference hai jo kisi UTF-8 encoded string data ko point karta hai.

Example:

```
let s = "hello";
```

Yahan:

```
"hello"
   ↓
string literal
   ↓
&str
```

### String literal

String literal:

```
"hello"
```

program ke binary mein stored hota hai.

Isliye string literal ek string slice hota hai:

```
"hello"
   ↓
  &str
```

🧠 MENTAL MODEL

```
&str
  ↓
borrowed view of string data
  ↓
ownership nahi rakhta
```

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 2. `String` TYPE

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

`String` Rust standard library ka type hai.

Rust Book ke according `String`:

```
growable
mutable
owned
UTF-8 encoded
```

string type hai.

### TERMINOLOGY

🔹 growable

```
Size ko increase kiya ja sakta hai.
```

Example:

```
"foo"
  ↓
"foobar"
```

🔹 mutable

```
Existing String ke contents change/add kiye ja sakte hain.
```

Example:

```
let mut s = String::from("foo");

s.push_str("bar");
```

🔹 owned

```
`String` underlying string data ki ownership rakhta hai.
```

Isliye:

```
String
```

aur:

```
&str
```

mein ownership ka major difference hai.

🧠 QUICK COMPARISON

```
String
   │
   ├── owns data
   ├── growable
   ├── mutable
   └── UTF-8

&str
   │
   ├── borrows data
   ├── does not own data
   └── UTF-8
```

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 3. STRING ACTUALLY KIS TYPE KI COLLECTION HAI?

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

`String` ko collections ke chapter mein discuss kiya jaata hai because
internally:

```
String
   ↓
wrapper around Vec<u8>
   ↓
collection of bytes
```

Yaani String ke andar text ultimately bytes ke form mein stored hota hai.

`String` ko roughly:

```
Vec<u8> + extra guarantees/restrictions/capabilities
```

ki tarah mentally model kar sakte ho.

⚠️ "roughly" important hai.

`String` literally bas ek normal `Vec<u8>` nahi hai. It provides extra
guarantees and functionality so that the bytes represent valid UTF-8.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 4. CREATING A NEW `String`

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

`String` ke paas `new()` function hai.

Example:

```
fn main() {
    let mut s = String::new();
}
```

Iska result:

```
s
↓
empty String
```

Yaani initially:

```
s = ""
```

### `mut` KYUN?

Because hum baad mein String mein data add karna chahte hain.

```
let mut s = String::new();

s
↓
empty String
↓
later can grow
```

Agar sirf:

```
let s = String::new();
```

likha aur baad mein modify karne ki koshish ki, to mutable binding ki
requirement aayegi.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 5. `to_string()` SE STRING CREATE KARNA

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Agar initial data already available hai, `to_string()` use kar sakte hain.

Example:

```
fn main() {
    let data = "initial contents";

    let s = data.to_string();
}
```

Flow:

```
data
  ↓
"initial contents"
  ↓
&str
  ↓
.to_string()
  ↓
String
```

Directly literal par bhi:

```
let s = "initial contents".to_string();
```

### `to_string()` KYUN AVAILABLE HAI?

`to_string()` un types par available hota hai jo `Display` trait implement
karte hain.

String literals `Display` implement karte hain.

Isliye:

```
"initial contents".to_string()
```

valid hai.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 6. `String::from()`

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Same String create karne ka doosra common method:

```
String::from()
```

Example:

```
fn main() {
    let s = String::from("initial contents");
}
```

Flow:

```
"initial contents"
        ↓
      &str
        ↓
String::from(...)
        ↓
      String
```

### `to_string()` vs `String::from()`

Dono is situation mein same result dete hain:

```
let s = "initial contents".to_string();

let s = String::from("initial contents");
```

So:

```
String::from("hello")
```

and:

```
"hello".to_string()
```

dono `"hello"` contents wali `String` create kar sakte hain.

Rust Book ke according kaunsa use karna hai mainly:

```
style
+
readability
```

ka matter hai.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 7. STRINGS UTF-8 ENCODED HOTI HAIN

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Ye poore section ka most important concept hai.

Rust Strings:

```
UTF-8 encoded
```

hoti hain.

### UTF-8 kya hai?

UTF-8 ek encoding system hai jo Unicode text ko bytes ke form mein
represent karta hai.

Simple mental model:

```
Human-readable text
        ↓
     Unicode
        ↓
      UTF-8
        ↓
      bytes
        ↓
  computer memory
```

Isliye String ko sirf:

```
"English characters ka array"
```

samajhna galat hai.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 8. DIFFERENT LANGUAGES KO STRING MEIN STORE KAR SAKTE HAIN

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

UTF-8 ki wajah se Rust String different languages ka properly encoded
text store kar sakti hai.

Example:

```
fn main() {
    let hello = String::from("السلام عليكم");
    let hello = String::from("Dobrý den");
    let hello = String::from("Hello");
    let hello = String::from("שלום");
    let hello = String::from("नमस्ते");
    let hello = String::from("こんにちは");
    let hello = String::from("안녕하세요");
    let hello = String::from("你好");
    let hello = String::from("Olá");
    let hello = String::from("Здравствуйте");
    let hello = String::from("Hola");
}
```

Ye sab valid `String` values hain.

🧠 IMPORTANT

```
UTF-8
   ↓
ASCII tak limited nahi hai
   ↓
multiple writing systems supported
```

Isliye:

```
English
Hindi
Japanese
Korean
Chinese
Arabic
Hebrew
Cyrillic
etc.
```

sab UTF-8 Strings mein store ho sakte hain, provided data properly encoded
ho.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 9. UTF-8 KO SAMJHNE KE LIYE 3 LEVELS

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Rust ke perspective se string data ko teen important ways mein dekha ja
sakta hai:

```
1. Bytes
2. Unicode scalar values
3. Grapheme clusters
```

Ye teen same cheez nahi hain.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

## 🔹 LEVEL 1 — BYTES

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Computer ultimately string ko bytes ke form mein store karta hai.

Example Hindi word:

```
"नमस्ते"
```

UTF-8 encoded bytes:

```
[224, 164, 168, 224, 164, 174, 224, 164, 184,
 224, 165, 141, 224, 164, 164, 224, 165, 135]
```

Total:

```
18 bytes
```

Yaani:

```
"नमस्ते"
```

human ko ek word dikhta hai,

but computer memory mein:

```
18 bytes
```

stored hain.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

## 🔹 LEVEL 2 — UNICODE SCALAR VALUES

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Rust ka:

```
char
```

Unicode scalar value represent karta hai.

Same:

```
"नमस्ते"
```

ko Unicode scalar values ke form mein dekho:

```
['न', 'म', 'स', '्', 'त', 'े']
```

Total:

```
6 char values
```

### Lekin ek important detail

Ye 6 `char` values mein sab actual standalone letters nahi hain.

```
'न'
'म'
'स'
'्'
'त'
'े'
```

`्` aur `े` diacritics hain.

### TERMINOLOGY

🔹 diacritic

```
Ek mark/sign jo kisi letter ke pronunciation ya appearance ko
modify karta hai.
```

Important:

```
char
  ≠
human-perceived character
```

Ye distinction bahut important hai.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

## 🔹 LEVEL 3 — GRAPHEME CLUSTERS

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Grapheme cluster ko roughly human-perceived character ke closest concept
ke roop mein samajh sakte ho.

Same:

```
"नमस्ते"
```

grapheme clusters ke form mein:

```
["न", "म", "स्", "ते"]
```

Total:

```
4 grapheme clusters
```

Ab comparison dekho:

```
HUMAN VIEW
    ↓
4 grapheme clusters

Rust char view
    ↓
6 Unicode scalar values

COMPUTER STORAGE
    ↓
18 UTF-8 bytes
```

🔥 THIS IS THE CORE STRING MENTAL MODEL

```
"नमस्ते"

    ↓

┌─────────────────────────────┐
│ Grapheme clusters           │
│ ["न", "म", "स्", "ते"]      │
│             = 4            │
└─────────────────────────────┘

    ↓

┌─────────────────────────────┐
│ Unicode scalar values       │
│ ['न','म','स','्','त','े']   │
│             = 6            │
└─────────────────────────────┘

    ↓

┌─────────────────────────────┐
│ UTF-8 bytes                 │
│ [224,164,168,...]           │
│             = 18           │
└─────────────────────────────┘
```

⚠️ SAME TEXT

but:

```
byte count
≠
char count
≠
grapheme count
```

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 10. RUST STRING INDEXING ALLOW KYUN NAHI KARTA?

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Other programming languages mein commonly:

```
string[0]
```

ka matlab first character hota hai.

Rust mein:

```
let s1 = String::from("hi");
let h = s1[0];
```

valid nahi hai.

Why?

Because Rust ko decide karna padega:

```
s[0]
```

actually kya return kare?

Possible interpretations:

```
0th BYTE?
    ↓
104

0th Unicode scalar value?
    ↓
'h'

0th grapheme cluster?
    ↓
"h"

String slice?
    ↓
&str
```

Problem:

```
integer index ka meaning ambiguous hai.
```

hai.

lagte hain.

       ↓

       ↓

208

# 14. BYTE BOUNDARY KYA HAI?

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Isliye har byte position ek valid character boundary nahi hoti.

Example:

```
З
```

UTF-8:

```
[208, 151]
```

Yahan:

```
byte index 0
    ↓
character ka beginning

byte index 1
    ↓
character ke beech mein

byte boundary

# 15. STRING SLICING

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Rust integer indexing allow nahi karta:

```
s[0]       ❌
```

Lekin range indexing se String slice create kar sakte ho:

```
&hello[0..4]
```

Example:

```
let hello = "Здравствуйте";

let s = &hello[0..4];
```

Yahan:

```
0..4
```

characters ka range nahi hai.

Ye:

```
BYTE RANGE
```

hai.

Since `"З"` aur `"д"` each 2 bytes lete hain:

```
З → bytes 0..2
д → bytes 2..4
```

Therefore:

```
&hello[0..4]
```

returns:

```
"Зд"
```

as a `&str`.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 16. ⚠️ INVALID STRING SLICE

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Suppose:

```
let hello = "Здравствуйте";
```

Ab:

```
let s = &hello[0..1];
```

Problem:

```
З
```

takes:

```
2 bytes
```

But hum:

```
0..1
```

slice kar rahe hain.

Yaani character ke sirf first byte ko le rahe hain.

Visual:

```
З
├──────────┤
byte 0    byte 1

0..1
└────┘
only half of character
```

Ye valid UTF-8 string slice nahi hai.

Therefore Rust runtime par panic karega.

Error conceptually:

```
byte index 1 is not a char boundary;
it is inside 'З' (bytes 0..2)
```

🔥 IMPORTANT

String slicing mein range:

```
character indices
```

nahi hoti.

Range:

```
BYTE INDICES
```

hoti hai.

And every endpoint must lie on a valid UTF-8 character boundary.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 19. STRING INDEXING KI SECOND PROBLEM — O(1)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Rust integer indexing allow nahi karta sirf ambiguity ki wajah se nahi.

Ek aur important reason hai:

```
PERFORMANCE
```

Normally programmers expect karte hain:

```
array[0]
```

to:

```
O(1)
```

time mein element mil jaaye.

### O(1) kya hota hai?

```
O(1)
  =
constant time
```

Yaani input size badhne par operation ka time theoretically same order mein
rehta hai.

For a normal array:

```
array[0]
```

direct memory location calculate ki ja sakti hai.

But String mein UTF-8 characters variable number of bytes use kar sakte hain.

Suppose:

```
character A → 1 byte
character B → 1 byte
character C → 3 bytes
character D → 2 bytes
```

Agar tum poochho:

```
"mujhe 5th character do"
```

to Rust directly:

```
5th byte
```

par jump nahi kar sakta.

Usko beginning se walk karke determine karna padega:

```
byte 0
   ↓
character boundary?
   ↓
next bytes
   ↓
next character
   ↓
...
   ↓
5th character
```

Therefore arbitrary character indexing ko guaranteed O(1) banana possible
nahi hai.

🔥 CORE REASON

```
UTF-8
  ↓
variable-width encoding
  ↓
character = variable number of bytes
  ↓
character N locate karne ke liye beginning se scan karna pad sakta hai
  ↓
not guaranteed O(1)
```

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

```
"Memory mein kitne bytes hain?"
    ↓
bytes


"Kitne Unicode scalar values hain?"
    ↓
chars


"Kitne human-perceived characters hain?"
    ↓
grapheme clusters
```

```

   ↓
18


chars
   ↓
6


grapheme clusters
   ↓

Ye numbers different hain because they represent different levels of

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 25. `char` ≠ HUMAN CHARACTER

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Ye subtle but extremely important hai.

Rust:

```
char
```

Unicode scalar value represent karta hai.

Lekin human language mein:

```
"character"
```

ka matlab often ek visually perceived letter/symbol hota hai.

Ye same thing nahi hai.

Example:

```
"नमस्ते"
```

Rust `char`s:

```
['न', 'म', 'स', '्', 'त', 'े']
```

Human-perceived grapheme clusters:

```
["न", "म", "स्", "ते"]
```

Therefore:

```
char
   ≠
grapheme cluster
```

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 26. GRAPHEME CLUSTERS STANDARD LIBRARY MEIN KYUN NAHI?

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Grapheme clusters identify karna complex hai.

Unicode mein visually ek character banne ke liye multiple Unicode scalar
values combine ho sakte hain.

Isliye Rust standard library directly grapheme-cluster functionality
provide nahi karti.

Agar application ko grapheme clusters ke saath kaam karna hai:

```
crates.io
```

par available crates use kiye ja sakte hain.

🧠 IMPORTANT

```
Rust std
   ↓
bytes support
   ↓
chars support
   ↓
grapheme clusters
   ↓
more complex
   ↓
external crates may be needed
```

# 27. `String` INDEXING KA COMPLETE MENTAL MODEL

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Jab tum likhte ho:

```

```

to tum implicitly pooch rahe ho:

```

```

```

  ↓
ambiguous meaning
  +
variable-width UTF-8
  +
O(1) expectation problem
  ↓
Rust rejects integer indexing
```

s1
 │

 ↓

 ↓

s1 → MOVED ❌

# 32. DEREF COERCION — COMPLETE MENTAL MODEL

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

We have:

```
s2 : String
```

Therefore:

```
&s2 : &String
```

But `add()` wants:

```
&str
```

Rust automatically performs deref coercion:

```
&String
   ↓
deref coercion
   ↓
&str
```

Conceptually:

```
&s2
  ↓
&s2[..]
```

This is why:

```
s1 + &s2
```

works even though:

```
&s2
```

is technically `&String`.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 33. WHY `format!` IS OFTEN CLEANER

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Suppose:

```
let s1 = String::from("tic");
let s2 = String::from("tac");
let s3 = String::from("toe");
```

Using `+`:

```
let s = s1 + "-" + &s2 + "-" + &s3;
```

It works.

But:

```
+ + + &
" " " "
```

ke wajah se code visually cluttered ho sakta hai.

Using `format!`:

```
let s = format!("{s1}-{s2}-{s3}");
```

Much easier to read:

```
s1
↓
-
↓
s2
↓
-
↓
s3
```

And importantly:

```
format!
```

doesn't take ownership of its parameters.

So:

```
s1 ──borrow──┐
s2 ──borrow──┼──> format!
s3 ──borrow──┘
                ↓
            new String
```

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 36. COMMON MISCONCEPTIONS

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

❌ MISCONCEPTION 1:

```
String = array of characters
```

✅ CORRECT:

```
String = UTF-8 encoded bytes with String-specific guarantees
         and functionality.
```

────────────────────────────────────────────────────────────────────

❌ MISCONCEPTION 2:

```
&str owns the string
```

✅ CORRECT:

```
&str is a borrowed string slice.

It does not own the underlying data.
```

────────────────────────────────────────────────────────────────────

❌ MISCONCEPTION 3:

```
String length = number of characters
```

✅ CORRECT:

```
String length is based on bytes.

Unicode scalar value count and grapheme-cluster count can be different.
```

────────────────────────────────────────────────────────────────────

❌ MISCONCEPTION 4:

```
`char` = human-visible character
```

✅ CORRECT:

```
`char` = Unicode scalar value.

One human-perceived character can involve multiple scalar values.
```

────────────────────────────────────────────────────────────────────

❌ MISCONCEPTION 5:

```
`s[0]` should obviously mean first character
```

✅ CORRECT:

```
"first" could mean byte, scalar value, grapheme cluster, or slice.

Rust therefore does not allow integer indexing.
```

────────────────────────────────────────────────────────────────────

❌ MISCONCEPTION 6:

```
`s1 + &s2` copies both complete Strings
```

✅ CORRECT:

```
`s1` is moved into `add()`,
`s2` is borrowed,
contents of `s2` are appended,
and the resulting String is returned.
```

────────────────────────────────────────────────────────────────────

❌ MISCONCEPTION 7:

```
`&hello[0..1]` means first character
```

✅ CORRECT:

```
String ranges are BYTE ranges.

If the range cuts through a UTF-8 character,
the program panics.
```

────────────────────────────────────────────────────────────────────

❌ MISCONCEPTION 8:

```
`.chars()` gives human-perceived characters
```

✅ CORRECT:

```
`.chars()` gives Unicode scalar values.

Grapheme clusters are a different concept.
```

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 37. STEP-BY-STEP EXAMPLE — `"नमस्ते"`

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Take:

```
let s = String::from("नमस्ते");
```

STEP 1:

```
Human sees:

    नमस्ते
```

STEP 2:

```
Text is represented using Unicode.
```

STEP 3:

```
Unicode text is encoded using UTF-8.
```

STEP 4:

```
UTF-8 stores it as bytes:

    [224, 164, 168, 224, 164, 174, 224, 164, 184,
     224, 165, 141, 224, 164, 164, 224, 165, 135]
```

STEP 5:

```
Total:

    18 bytes
```

STEP 6:

```
Interpret as Unicode scalar values:

    ['न', 'म', 'स', '्', 'त', 'े']
```

STEP 7:

```
Total:

    6 char values
```

STEP 8:

```
Interpret as grapheme clusters:

    ["न", "म", "स्", "ते"]
```

STEP 9:

```
Total:

    4 grapheme clusters
```

Therefore:

```
SAME STRING

┌──────────────────────────────┐
│ UTF-8 bytes                  │
│              = 18           │
├──────────────────────────────┤
│ Unicode scalar values       │
│              = 6            │
├──────────────────────────────┤
│ Grapheme clusters           │
│              = 4            │
└──────────────────────────────┘
```

```
string[index]
```

🧠 FINAL MENTAL MODEL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

                           │
                           ↓

                           ↓

                 ↓                   ↓

`String`

```
├── owned
├── growable
├── mutable
├── UTF-8 encoded

```

`&str`

```

├── does not own data

     ↓
empty String

String

```

# 39. 🔥 GOLDEN RULES

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. 🔥 `String` is an owned, growable, mutable, UTF-8 encoded string type.

2. 🔥 `&str` is a borrowed string slice; it does not own the data.

3. 🔥 String data is ultimately stored as UTF-8 bytes.

4. 🔥 UTF-8 characters can use different numbers of bytes.

5. 🔥 `String` is NOT simply an array of characters.

6. 🔥 `String` integer indexing like `s[0]` is not allowed.

7. 🔥 String indexing is ambiguous because "character" could mean:
   byte
   Unicode scalar value
   grapheme cluster
   string slice

8. 🔥 UTF-8 also prevents guaranteed O(1) character indexing because
   Rust may need to scan from the beginning to find the boundary.

9. 🔥 `push_str()` appends a string slice.

10. 🔥 `push()` appends one `char`.

11. 🔥 `s1 + &s2` moves `s1` but borrows `s2`.

12. 🔥 `+` internally uses the `add()` method.

13. 🔥 `add()` takes ownership of `self`.

14. 🔥 `&String` can be automatically coerced to `&str` through
    deref coercion.

15. 🔥 `format!` returns a new `String` and does not take ownership of
    its parameters.

16. 🔥 String slicing uses BYTE ranges, not character ranges.

17. 🔥 A string slice must start and end at valid UTF-8 boundaries.

18. 🔥 Slicing through the middle of a UTF-8 character causes a panic.

19. 🔥 `.bytes()` gives raw UTF-8 bytes.

20. 🔥 `.chars()` gives Unicode scalar values.

21. 🔥 `char` does NOT necessarily equal a human-perceived character.

22. 🔥 Grapheme clusters are closer to what humans perceive as characters.

23. 🔥 Grapheme-cluster handling is more complex and is not directly
    provided by the Rust standard library.

24. 🔥 When working with Strings, first decide WHAT level of data you need:
    bytes, chars, or grapheme clusters.

# 41. 📌 MOST IMPORTANT CODE TO REMEMBER

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

### Create String

```
let mut s = String::new();

let s = String::from("hello");

let s = "hello".to_string();
```

### Append String Slice

```
let mut s = String::from("foo");

s.push_str("bar");

// s = "foobar"
```

### Append Character

```
let mut s = String::from("lo");

s.push('l');

// s = "lol"
```

### Concatenate

```
let s1 = String::from("Hello, ");
let s2 = String::from("world!");

let s3 = s1 + &s2;

// s1 moved
// s2 still valid
// s3 = "Hello, world!"
```

### Multiple Strings

```
let s1 = String::from("tic");
let s2 = String::from("tac");
let s3 = String::from("toe");

let s = s1 + "-" + &s2 + "-" + &s3;
```

### Cleaner Multiple Concatenation

```
let s = format!("{s1}-{s2}-{s3}");
```

### Iterate Over Unicode Scalar Values

```
for c in "Зд".chars() {
    println!("{c}");
}
```

### Iterate Over Bytes

```
for b in "Зд".bytes() {
    println!("{b}");
}
```

### String Slice

```
let hello = "Здравствуйте";

let s = &hello[0..4];

// s = "Зд"
```

### Invalid Slice

```
let s = &hello[0..1];

// ❌ panic
// cuts through the middle of a UTF-8 character
```

# 43. 🔥 FINAL TAKEAWAY

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Rust String ko samajhne ka sabse important point ye hai:

```
STRING ≠ CHARACTER ARRAY
```

Instead:

```
String
   ↓
UTF-8 encoded data
   ↓
bytes
   ↓
can be interpreted as:
   │
   ├── bytes
   ├── Unicode scalar values (`char`)
   └── grapheme clusters
```

Aur isi wajah se Rust tumhe force karta hai ki tum explicitly batao:

```
"Mujhe raw bytes chahiye"
    → bytes()

"Mujhe Unicode scalar values chahiye"
    → chars()

"Mujhe ek valid UTF-8 slice chahiye"
    → &s[start..end]

"Mujhe human-perceived characters chahiye"
    → grapheme-cluster functionality
```

Ye extra explicitness initially annoying lag sakti hai, lekin Rust ka
purpose yahi hai ki UTF-8 related mistakes ko silently allow karne ke
instead programmer ko correct interpretation choose karni pade.
