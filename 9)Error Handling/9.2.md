# 🦀 RECOVERABLE ERRORS — `Result`
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

## 🔄 1. `panic!` vs `Result`

Har error serious nahi hota.

Example:

    File open karni hai
         ↓
    File exist nahi karti
         ↓
    Program ko crash karna zaroori nahi
         ↓
    Maybe file create kar do

Isliye Rust mein:

    panic!
        → unrecoverable problem
        → program stops

    Result
        → recoverable/handleable problem
        → caller decide kar sakta hai kya karna hai


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

## 📦 2. `Result<T, E>` KYA HAI?

`Result` ek enum hai:

    enum Result<T, E> {
        Ok(T),
        Err(E),
    }

Iske 2 possible outcomes hain:

    Ok(T)
      ↓
    Success

    Err(E)
      ↓
    Failure

`T` = success mein milne wali value ka type

`E` = error ka type

Example:

    Result<String, io::Error>

means:

    Success → String
    Failure → io::Error

⚠️ `Result<String, io::Error>` ka matlab sirf `String` return
karna nahi hai.

Function dono mein se koi ek return kar sakti hai:

    Ok(String)

OR

    Err(io::Error)


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

## 📂 3. `File::open()` KA `Result`

    let greeting_file_result = File::open("hello.txt");

`File::open()` roughly return karta hai:

    Result<File, io::Error>

Meaning:

    File open hui?
        ↓
    ┌───────┴───────┐
    ↓               ↓
    Ok(file)     Err(error)
    ↓               ↓
  success         failure

File exist karti hai:

    Ok(file)

File missing / permission problem etc.:

    Err(error)


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

## 🎯 4. `match` SE `Result` HANDLE KARNA

    let greeting_file = match greeting_file_result {
        Ok(file) => file,
        Err(error) => panic!("Problem opening the file: {error:?}"),
    };

Logic:

    Result
      ↓
    ┌───┴────┐
    ↓        ↓
   Ok       Err
    ↓        ↓
  file     panic!


### `Ok(file) => file`

Success hua → actual file handle nikaal lo.

### `Err(error) => ...`

Failure hua → error ke according action lo.

Yahan example mein `panic!` kiya gaya hai,
lekin zaroori nahi ki har `Err` par panic hi karein.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

## 🧩 5. DIFFERENT ERRORS KO DIFFERENTLY HANDLE KARNA

`File::open()` multiple reasons se fail ho sakta hai:

    File missing
    Permission denied
    Other I/O problem
    ...

Hum keh sakte hain:

    File missing?
        ↓
    File create karo.

    Koi aur error?
        ↓
    panic!


Iske liye:

    error.kind()

use hota hai.

Example:

    match error.kind() {
        ErrorKind::NotFound => {
            // file create karo
        }

        _ => {
            // other error
            panic!(...)
        }
    }

`ErrorKind::NotFound` ka matlab:

    File exist nahi karti.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

## 🔀 6. NESTED `match` KA FLOW

    File::open()
         ↓
    ┌────┴─────┐
    ↓          ↓
   Ok         Err
    ↓          ↓
  file      error.kind()
               ↓
          ┌────┴────┐
          ↓         ↓
      NotFound    Other
          ↓         ↓
    File::create  panic
          ↓
       ┌──┴──┐
       ↓     ↓
      Ok    Err
       ↓     ↓
     file   panic


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

## 🧹 7. `unwrap_or_else()`

Nested `match` kaafi verbose ho sakta hai.

Same logic ko `unwrap_or_else()` se shorter likh sakte hain.

    File::open("hello.txt").unwrap_or_else(|error| {
        ...
    });

Abhi iska simple idea:

    `match`
       ↓
    manually handle Result

    `unwrap_or_else()`
       ↓
    same type ka handling, but shorter

Closures (`|error|`) ko Chapter 13 mein detail mein cover kiya jayega.

## ⚡ 8. `unwrap()`

Agar tum simply bolna chahte ho:

> Success hua toh value de,
> failure hua toh panic kar.

Use:

    let greeting_file = File::open("hello.txt").unwrap();

Conceptually:

    match result {
        Ok(value) => value,
        Err(_) => panic!(),
    }

So:

    Ok(file)
       ↓
    unwrap()
       ↓
    file

    Err(error)
       ↓
    unwrap()
       ↓
    panic!


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

## 📝 9. `expect()` — `unwrap()` WITH CUSTOM MESSAGE

    let greeting_file = File::open("hello.txt")
        .expect("hello.txt should be included in this project");

Behavior:

    Ok(file)
       ↓
    file

    Err(error)
       ↓
    panic + custom message

### Difference:

    unwrap()
        → default panic message

    expect("message")
        → custom meaningful message

Production-quality code mein `expect()` often useful hota hai
kyunki failure hone par debugging ke liye extra context milta hai.

# 📤 10. ERROR PROPAGATION KYA HAI?

Suppose:

    main()
      ↓
    read_username_from_file()
      ↓
    File::open()

Agar `File::open()` fail ho:

    File::open()
         ↓
    Err(error)

Ab `read_username_from_file()` ke paas do choices hain:

    1. Khud error handle kare
    2. Error caller ko return kare

Agar second option:

    File::open()
         ↓
    Err(error)
         ↓
    read_username_from_file()
         ↓
    Err(error)
         ↓
    main()

Isko **error propagation** kehte hain.

### 🧠 Simple Meaning

**Error ko caller ko propagate karna = current function error ko
khud solve/handle na karke us error ko calling function ko return kar de.**

Caller phir decide karta hai:

    panic?
    default value?
    retry?
    alternative source?


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 🎯 11. `Result<String, io::Error>` YAHAN IMPORTANT HAI

Function:

    fn read_username_from_file() -> Result<String, io::Error>

already promise karti hai:

    Success → String
    Failure → io::Error

Therefore dono valid hain:

    Ok(username)

AND:

    Err(error)

Example:

    Ok("Kushagra".to_string())

ya:

    Err(io_error)


### 🧠 Remember

    Result<String, io::Error>

does NOT mean:

    "always return String"

It means:

    "either return String inside Ok,
     or return io::Error inside Err."


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# ❓ 12. `?` OPERATOR KYA KARTA HAI?

`?` error propagation ka shortcut hai.

Example:

    let file = File::open("hello.txt")?;

Conceptually:

    File::open()
         ↓
       Result
       /    \
     Ok      Err
     ↓        ↓
   value    return Err
     ↓        ↓
  continue   caller


### Simple meaning:

    `Ok(value)`
        → value nikaalo aur continue karo

    `Err(error)`
        → current function se Err return karo


⚠️ `?` error ko solve nahi karta.

⚠️ `?` normally panic bhi nahi karta.

It simply **error ko caller tak propagate karta hai.**


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 🔥 13. `?` KYUN KAAM KARTA HAI `Result` RETURNING FUNCTION MEIN?

Example:

    fn read_username_from_file() -> Result<String, io::Error> {

        let file = File::open("hello.txt")?;

        ...

    }

Function ka return type:

    Result<String, io::Error>

Agar:

    File::open()

returns:

    Err(io::Error)

to `?` current function se:

    Err(io::Error)

return kar sakta hai.

Kyunki function ka return type already `Result` hai.

So:

    Function promises:

    Result<String, io::Error>

             ↓

    `?` can return:

    Err(io::Error)

             ↓

    COMPATIBLE ✅


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# ❌ 14. NORMAL `main()` MEIN `?` KYUN NAHI CHALTA?

Normal:

    fn main() {
        let file = File::open("hello.txt")?;
    }

`main()` ka return type:

    ()

Matlab:

    main() promises → ()

Lekin `?` error aane par karna chahta hai:

    return Err(io::Error)

Ab:

    Expected:
        ()

    But `?` wants:
        Err(io::Error)

Mismatch:

    () ≠ Result<..., io::Error>

Therefore:

    ❌ Compile error


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# ✅ 15. PREVIOUS EXAMPLE MEIN COMPATIBILITY KYUN THI?

Ye:

    fn read_username_from_file()
        -> Result<String, io::Error>

already `Result` return karta hai.

Isliye:

    File::open("hello.txt")?

allowed hai.

Flow:

    File::open()
         ↓
       Result
       /    \
     Ok      Err
     ↓        ↓
   value    return Err
     ↓        ↓
  continue  caller


Normal `main()`:

    fn main() { ... }

returns:

    ()

So:

    File::open()?
         ↓
    Err(io::Error)
         ↓
    main() wants to return ()
         ↓
    ❌ incompatible


### 🧠 CORE RULE

**`?` current function se error return karta hai,
isliye current function ka return type us error ko return karne
ke compatible hona chahiye.**


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 📖 16. ERROR PROPAGATION KA FULL EXAMPLE

    fn read_username_from_file() -> Result<String, io::Error> {

        let mut username_file =
            File::open("hello.txt")?;

        let mut username = String::new();

        username_file
            .read_to_string(&mut username)?;

        Ok(username)
    }

Flow:

    File::open()
         ↓
    ┌────┴────┐
    ↓         ↓
   Ok        Err
    ↓         ↓
  file    return Err
    ↓         ↓
continue   caller


Then:

    read_to_string()
         ↓
    ┌────┴────┐
    ↓         ↓
   Ok        Err
    ↓         ↓
 username  return Err
    ↓         ↓
 continue   caller

Finally:

    Ok(username)

# 🔗 17. `?` CHAINING

Ye:

    let mut username_file =
        File::open("hello.txt")?;

    username_file
        .read_to_string(&mut username)?;

shorter likh sakte hain:

    File::open("hello.txt")?
        .read_to_string(&mut username)?;

Same logic hai.

Pehle file open hoti hai.

Agar successful:

    `?` → File value

Then us file par:

    read_to_string()

call hota hai.

Agar kisi step par error:

    `?` → Err return to caller.

# 📚 18. `fs::read_to_string()` — READY-MADE SHORTCUT

Agar simply file ko String mein read karna hai:

    fn read_username_from_file() -> Result<String, io::Error> {
        fs::read_to_string("hello.txt")
    }

`fs::read_to_string()` internally:

    open file
       ↓
    create String
       ↓
    read contents
       ↓
    return String / error

provide karta hai.

Isliye manually `File::open()` + `read_to_string()` likhne ki
zaroorat nahi.

# ⚠️ 19. `?` + RETURN TYPE RULE

`?` sirf compatible return type wali function mein use ho sakta hai.

### Result:

    fn foo() -> Result<T, E> {
        some_operation()?;
    }

    ✅


### Option:

    fn foo() -> Option<T> {
        some_option?;
    }

    ✅


### Normal `()`:

    fn foo() {
        some_result?;
    }

    ❌


### 🧠 Rule

    Result par `?`
        → function should return compatible Result

    Option par `?`
        → function should return Option

Automatically:

    Result → Option
    Option → Result

convert nahi hota.

# 🔢 20. `main()` KO `Result` RETURN KARWA SAKTE HAIN

Instead of:

    fn main() {
        ...
    }

you can write:

    fn main() -> Result<(), Box<dyn Error>> {
        let greeting_file = File::open("hello.txt")?;

        Ok(())
    }

Ab `main()` ka return type:

    Result<(), Box<dyn Error>>

hai.

Therefore `?` allowed hai.

### `Box<dyn Error>`

Abhi simple terms mein:

    "kisi bhi type ka error"

Samajh sakte ho.

# 🚦 21. `main()` KA EXIT CODE

Agar:

    main() → Ok(())

program successfully exit karta hai:

    exit code = 0

Agar:

    main() → Err(...)

to:

    exit code = non-zero

Convention:

    0
    ↓
    success

    non-zero
    ↓
    error

# 🔵 22. `?` WITH `Option`

`?` `Option` ke saath bhi use ho sakta hai.

Example:

    fn last_char_of_first_line(text: &str) -> Option<char> {
        text.lines().next()?.chars().last()
    }

Agar first line nahi mili:

    next()
      ↓
    None
      ↓
    ?
      ↓
    function returns None

Agar first line mili:

    next()
      ↓
    Some(line)
      ↓
    ?
      ↓
    line extract
      ↓
    continue


### Important

    Result + ? → function returns Result

    Option + ? → function returns Option

Mix nahi kar sakte automatically.

# 🧠 FINAL MENTAL MODEL

                 RESULT<T, E>
                      │
              ┌───────┴───────┐
              ↓               ↓
           Ok(T)            Err(E)
              ↓               ↓
           success          failure
                              │
                     ┌────────┴────────┐
                     ↓                 ↓
                  handle            propagate
                     │                 │
                  match /          `?`
                  methods             │
                                      ↓
                               caller ko Err


### `panic!`

    Error
      ↓
    crash/terminate


### `unwrap()`

    Ok → value
    Err → panic


### `expect()`

    Ok → value
    Err → panic + custom message


### `match`

    Ok  → tum decide karo
    Err → tum decide karo


### `?`

    Ok  → value + continue
    Err → current function se Err return

# ⭐ KEY TAKEAWAYS

🔹 `Result<T, E>` ke do variants hote hain: `Ok(T)` aur `Err(E)`.

🔹 `T` success value ka type hai aur `E` error ka type hai.

🔹 `Result<String, io::Error>` ka matlab hai:
   `Ok(String)` OR `Err(io::Error)`.

🔹 **Error propagation** ka matlab hai error ko current function mein
   handle karne ke bajay caller ko return kar dena.

🔹 `?` error propagation ka concise shortcut hai.

🔹 `?`:
   `Ok` → value nikaal kar continue karta hai.
   `Err` → current function se `Err` return karta hai.

🔹 `?` error ko fix nahi karta aur normally panic nahi karta.

🔹 `?` tabhi use ho sakta hai jab current function ka return type
   us value/error ko return karne ke compatible ho.

🔹 Isliye `Result` return karne wali function mein `?` valid hai,
   lekin normal `fn main() -> ()` mein nahi.

🔹 `unwrap()` = `Err` par panic.

🔹 `expect()` = `Err` par panic + custom message.

🔹 `match` se `Ok` aur `Err` ko manually handle kar sakte ho.

🔹 `main()` ko `Result<(), Box<dyn Error>>` return karwa kar `?`
   use kiya ja sakta hai.

🔹 `Result` ke saath `?` aur `Option` ke saath `?` alag contexts mein
   use hote hain; Rust automatically dono ko mix nahi karta.
